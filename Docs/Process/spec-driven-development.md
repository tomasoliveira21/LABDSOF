# Spec-Driven Development Rules

> LABDSOF 2026/27 · Sprint A · Assignment §8 (Development and Delivery Practices)
> **Status:** **[PROPOSED]** on 15 October 2026, to validate with the team. Once agreed, the two checklist items at the end move into [`definition-of-ready-and-done.md`](definition-of-ready-and-done.md).
> Related decisions: contract-first API (C7), events only between services (C4), hexagonal services (B5) in [`architecture-decisions-guide.md`](../Technical/architecture-decisions-guide.md).

## Why

The spec is the source of truth; code is what implements it. Every change is described and reviewed as a spec before it is written as code, so humans and AI assistants implement the same thing, and reviewers check code against something written down.

## Rules

| # | Rule |
|---|---|
| R1 | **No spec, no code.** Every user story has a spec in `specs/US-<nn>-<slug>.md`, written from the template below |
| R2 | **Spec first, in the same PR.** The PR (still 1 story = 1 issue = 1 PR) is opened as a draft with only the spec and the contract changes. Another member reviews and approves them before any implementation is pushed |
| R3 | **Contracts are part of the spec.** REST changes go in `backend/<service>/contracts/openapi.yaml`; events go in `backend/<service>/contracts/events/` (one JSON Schema per event). Contracts are written by hand |
| R4 | **Code is generated from contracts.** Server interfaces, DTOs and the frontend client are generated by `openapi-generator` at build time. Generated code is never edited or committed |
| R5 | **Every acceptance criterion has a test.** Each `AC-n` in the spec has at least one automated test whose name starts with `US-<nn> AC-<n>` |
| R6 | **Behaviour changes start in the spec.** A bug fix or change that alters behaviour updates the spec (and contract) in the same PR. Code that does something the spec does not say is rejected in review |
| R7 | **AI assistants implement from the spec.** The spec is the prompt. A human reviews the output against the spec like any other code |
| R8 | **Specs stay.** Merged specs are not deleted; a later story that changes the behaviour edits them and says so in its PR |

## Template

```markdown
# US-<nn> · <title>

**Issue:** #<n> · **Services:** <Auth & Users | Events | Reports | Transports | Badges | frontend>

## Story
As a <persona> I want <goal> so that <benefit>.

## Acceptance criteria
- **AC-1** Given … When … Then …
- **AC-2** …
- **AC-iso** Given a member of event Y, When they call this for event X, Then they get 403/404 (any story touching event data)

## Contracts
- REST: <operations added or changed in openapi.yaml>
- Events: <published / consumed>

## Data
<tables and Flyway migrations; backward compatible>

## Plan
<ports, use cases and adapters touched, per service>

## Out of scope
```

## Additions to DoR and DoD (after agreement)

- DoR: the story has a spec following this template.
- DoD Level 1: the spec was approved before implementation; every `AC-n` has a test; contracts updated.
