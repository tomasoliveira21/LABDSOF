## 1. Source

**Story:** as an **EventAdmin** (persona P3 · Sofia), I want to create, rename and delete the teams of my event (e.g. *Security*, *Nursing*), so that the event's organisation is reflected in Farol.

**This PR:** `GET`, `POST`, `PATCH` and `DELETE` on `/api/v1/events/{eventId}/teams[/{teamId}]` in Events, each publishing `TeamChanged` through the outbox, and the first permission check Events makes on a caller's teams. **Not in it:** the back-office team pages (the web app is Tomás Oliveira's, decision 13; what they need is written on #65); `PUT …/teams/{teamId}/permissions` and the report types of `Reports.Review` (US-17, #66); adding members to a team (US-18, #67, in Auth & Users); the queue and field-task consequences of a deletion, which are Reports' work when it consumes `TeamChanged` (US-29 to US-33, US-52, US-53).

| # | Acceptance criterion | Tests (name starts with `US-16 AC-<n>`) |
|---|---|---|
| AC-1 | Given I create a team with a name, then it appears in my event's team list, with no members and no permissions | `TeamServiceTest`, `TeamTest`, `TeamPermissionTest`, `TeamEventsTest`, `TeamsIT`, `JdbcTeamsIT`, `TeamContractIT` |
| AC-2 | Given a team name already exists in my event, when I create another with the same name, then it is refused | `TeamServiceTest`, `TeamTest`, `TeamsIT`, `JdbcTeamsIT` |
| AC-3 | Given I delete a team, then its members lose its permissions, and the requests routed to it go back to the control-room queue | `TeamServiceTest`, `TeamTest`, `TeamEventsTest`, `TeamsIT`, `JdbcTeamsIT`, `TeamContractIT` (Events' part: the team stops granting anything and `TeamChanged` carries `deleted: true` with a higher version, which Reports consumes) |

Renaming is part of AC-1's *team list* (the story's title names it, the acceptance criteria do not): `US-16 AC-1 …` covers it.

## 3. Decisions

| # | Decision | Options weighed and why |
|---|---|---|
| D1 | **`PATCH …/teams/{teamId}` ships whole here**, rename *and* `handledCategories` (stored and published); US-17 (#66) adds `PUT …/permissions`, the report types of `Reports.Review`, the audit of a permission change and the category → default-team reading. The contract already marks the operation *US-16, US-17* | The API outline gives one `PATCH` to both stories and the web app's form always sends both fields. *Rename only, `handledCategories` refused or ignored until #66:* leaves a half-built handler, a field the contract requires but the service drops, and a second round of tests over the same code. #66 is stacked on this branch, so nothing ships to `main` between the two unless the team merges this one alone — in which case the categories are already correct, only unused |
| D2 | **Team writes are refused while the event is `Suspended` or `Closed`**, with `409` and the detail *This event is not open to changes.*; reads keep #192 D5 (an EventAdmin sees any status). `Draft` and `Published` accept writes | US-09 says a suspended event *cannot be used*, and US-10 lets an EventAdmin edit *a draft or published event*; the same reading is applied to its teams. *Writes in any status:* no document forbids it and it needs no contract change, but an abandoned or misused event would keep being reorganised, and a closed event's history would still move. The cost is one `409` added to `DELETE` in `openapi.yaml` (`POST` and `PATCH` already declare it). **No document covers this:** flagged on the pull request and on #65 for the Product Owner |
| D3 | **A duplicate name is `409`**, compared ignoring case and surrounding blanks, among the teams **not deleted** of that event; a deleted team's name is free again. The name is stored as typed, trimmed | The contract says `409` *if the name is taken*, and `team_name_per_event` (#192 D4) is a partial unique index on `(event_id, lower(name)) WHERE deleted_at IS NULL`. **The index is the only check:** the adapter turns its `DuplicateKeyException` into `Write.NAME_TAKEN` and the service answers `409`. *Reading the name first and then writing:* one more query, one more branch, and the index would still have to decide the race between two creations of the same name, so the second path would be the one that is never tested. The same port reports a write that found **no live row any more** (`Write.GONE`), so a rename or a delete that loses the race against another delete answers `404` and publishes nothing, instead of claiming a change that did not happen and spending a version |
| D4 | **Who may read the list:** `EventAdmin`, or a member whose non-deleted teams in that event grant `HelpRequests.Triage` or `Reports.Review` (API outline §3). A member without them gets `403`; a non-member, a `Removed` member, a member of another event and a `FarolAdmin` who is not a member get the same `404` as an unknown event, and the refusal is logged (#192 D8). Writes are `EventAdmin` only | API outline §1.7: `403` is *no permission*, `404` is *not a member*. The permission is read from the local copies, never from the token (ADR-006): `membership_copy.team_ids` ∩ the event's non-deleted teams, then `team_permission`. This is the first such check in Events; Reports' `Team.grants` (#194 D12) is the model, and US-17 reuses it |
| D5 | **Delete is a soft delete**: `deleted_at` is set, the permissions rows are kept untouched, the version is bumped and `TeamChanged` carries `deleted: true` with the permissions it had. A second delete of the same team is `404` (it is no longer in the event's list) | #192 D4 chose the soft delete so `TeamChanged` can carry a higher version. Reports needs the deletion event to cancel the field tasks and return the routed requests (AC-3, domain model `FieldTask`), and Auth & Users needs it to stop accepting the team in US-18. *Hard delete:* loses the version that makes the consumers' `upsertIfNewer` work and breaks `team_permission`'s foreign key on rows other services still reference |
| D6 | **Every change bumps `team.version` and writes one `TeamChanged`** in the same transaction as the change (ADR-004), with the full state of §7.4 (`teamId`, `name`, `permissions` with `reportTypes`, `handledCategories`, `deleted`, `version`). `actorUserId` is the caller, `updated_by`/`updated_at` are stored | The consumers apply the copy only when the version is **strictly** newer (`LocalCopyService.upsertIfNewer`, #194), so a rename that did not bump the version would be dropped, and so would a later real change if the version had been spent. One `OutgoingEvent` factory, `TeamEvents.changed`, replaces the payload `EventContractIT` builds by hand today, which #192's comment required of this story |
| D7 | **`handledCategories` is a set, enforced in the domain:** a repeated category is `400`, the sent order is not kept, and the stored and published array follows the category's declaration order, so the payload is stable. The contract keeps a plain array with a `description` saying so, and **does not** use `uniqueItems` | The published event must satisfy `team.changed.schema.json`, whose `handledCategories` is `uniqueItems`, so the service must never publish a repeated one. `uniqueItems: true` in `openapi.yaml` looked like the way to say it, but **it was tried and rejected**: openapi-generator 7.27 then emits `Set<HelpCategory>` with `@JsonDeserialize(as = LinkedHashSet.class)`, which **deduplicates `["Health","Health"]` silently** instead of refusing it, and changes the response type too. Refusing is the house style (`additionalProperties: false`, an unknown field is already `400`), so the rule lives in `Team.categoriesOf`, where a test can see it |
| D8 | **An empty name, blanks only, or over 100 characters is `400`** before anything else; the generated model enforces the bounds, and the domain `Team` repeats them, so the rule is also tested where it ships. A missing `handledCategories` stays an empty list (#192 open point 6) and is **accepted** as *handles no category* | The table's `team_name` check (1 to 100 characters, not blank) is the same rule in the database. #192's open point 6 asked whether a missing list should be `400`: *handles no category* is the pilot's own *Control room* row (§4.4), so an empty list is valid, and the generated `[]` needs no fight with the generator |
| D9 | **No new Flyway migration.** `team` and `team_permission` come from `V1__events.sql` (#192 D4) | The tables, their checks and the partial unique index were written for this story. Keeping `V1` also avoids a renumbering race with the migration Bruno's #231 adds elsewhere |

## 6. Handoff and changelog

- **21 Nov 2026 · research (LISA, 233 s of a 600 s budget; stopped when the sources repeated).** Findings: everything structural was already in place (#192 D4, D6, D7), so this story is domain, application and adapters only; the cross-service consequences of a deletion are Reports'; three gaps needed deciding (D1, D2, D4) and are above. Also found: `ContractIT` and `SecurityIT` build their matrices from the contract, so the *fourteen operations* count drops to ten; `EventContractIT`'s hand-built `teamChanged(...)` had to move onto the real factory (D6); the CI smoke **cannot** cover this story, because nothing creates an event before US-06 (#61).
- **21 Nov 2026 · implementation**, in the order of §4, with `mvn clean verify` (JDK 21) green at the end: **162 unit and 519 integration tests**, JaCoCo **774/776 lines (99.7 %)** — the two missed are `EventsApplication.main` — and **202/202 branches (100 %)**, generated code included and no exclusion, PIT **113/113 mutations killed (100 %)**. No threshold lowered, no test disabled.
- **Three things the gates caught, each fixed at the root:**
  1. `uniqueItems: true` on `TeamChange.handledCategories` was written first, then **reverted after reading the generated code**: openapi-generator 7.27 emits `Set<HelpCategory>` with `@JsonDeserialize(as = LinkedHashSet.class)`, so `["Health","Health"]` would be deduplicated silently instead of refused, and the response type would change too (D7).
  2. `handledCategories: [null]` answered **500**: the web mapper called `getValue()` on the null item before the domain saw it. The mapper now passes the null on and `Team.categoriesOf` refuses it as a bad request (`400`).
  3. Two parallel deletes both answered `204` and wrote a **second `TeamChanged` with the same version**, which the consumers would silently drop. The port now reports `Write.GONE` when the `UPDATE … WHERE deleted_at IS NULL` affects no row, and the loser gets `404` with nothing published (D3, `JdbcTeamsIT`).
- **Not reproduced locally:** the Compose smoke run of `ci.yml`. This story adds no smoke step (nothing can create an event before US-06), and the stack was not rebuilt; CI covers it.
- **For #66 (US-17), stacked on this branch:** `PUT …/teams/{teamId}/permissions` writes `team_permission` and must bump `team.version` and publish one `TeamChanged` through `TeamEvents.changed`, which already carries the permissions and their report types; `Permission.carriesReportTypes()` and `TeamPermission`'s check are the rule for *report types only with `Reports.Review`*; the audit of *who and when* is already `team.updated_by`/`updated_at`; and `Permission.readsTeams()` is where the reading rule of D4 lives if US-17 widens it.
- **Open points left on the table:** (1) **D2 needs the Product Owner**, because no document says whether a suspended or closed event may still have its teams changed; (2) which team is the default when two handle the same category is still open in the domain model, and US-17 (#66) and US-29 meet it first; (3) `Docs/Product/mockups/` has no back-office team screens, which the Definition of Ready asks for (empty, loading, error); (4) the three non-blocking findings of Bruno's review of #192 (the consumer's `schemaVersion` check order, `ACCEPT_FLOAT_AS_INT`, and the missing log line when a message is dead-lettered after its last attempt) are untouched here and still deserve their own small pull request.
