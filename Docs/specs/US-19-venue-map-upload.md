## 1. Source

**Story:** as an **EventAdmin** (or a member with `Map.Edit`, persona P3 · Sofia), I want to upload the venue map as an image or PDF, so that participants and the team share the same reference.

**This PR:** `POST /api/v1/events/{eventId}/map-versions` — the upload, its hardening (ADR-007 decision 2, assessment M-11), the map version it stores on the volume and in the database, the points it copies from the previous version (API outline D5), the **first `VenueMapVersionPublished`** the product ever publishes, and the log line that records the upload. **Not in it:** reading the map and its image (US-21, #95 and the `current` operation), the points of interest themselves (US-20), the older version read by the control room (US-27), the map component of the web app (ADR-007 decisions 1, 4 and 5, Tomás), and the gateway-side size cap of ADR-013 L-4 (§7, open point).

## 3. Decisions

| # | Decision | Options weighed and why |
|---|---|---|
| D1 | **The type is read from the first bytes of the content**, never from the file name or the `Content-Type`: `\x89PNG\r\n\x1a\n`, `\xFF\xD8\xFF` and `%PDF-` are the three accepted signatures (`MapSourceType.ofContent`), and **anything else is `400`**, SVG included | ADR-007 decision 2 and assessment M-11 ask exactly this. *Apache Tika:* a dependency and a 60 MB model of file types to decide between three signatures that are four to eight bytes long, on a path that also has to refuse everything else; the three checks are five lines of domain code and are tested one byte at a time. *`Files.probeContentType`:* goes by the file name on most platforms, which is the attacker's input |
| D2 | **Every upload is re-encoded to PNG and scaled to at most 4096 px on the long side** (ADR-007 decision 2), through a `MapImages` port whose adapter is the only place that decodes anything. The re-encoding is what drops EXIF (a photo's GPS position), PDF metadata and any active content, so it happens even for a PNG that is already small | ADR-007 fixes it. Keeping the original file would also keep its metadata, and the migration of #192 already says the original is not kept. Scaling on read instead would mean every phone downloads the full raster |
| D3 | **The pixel limit of ADR-007 (left open there, *set with US-19*) is 25 megapixels**, read from the image header **before** the image is decoded (`ImageIO`'s reader gives the size without decoding) | A map is a plan or a scan: A0 at 300 dpi is 17 MP, a 2026 phone photo 12 MP, so 25 MP refuses nothing real. It is the decode that costs memory, not the file: 25 MP × 4 bytes is ~100 MB of heap at the peak, which the 512 MB the services run with (ADR-011) absorbs, while a 20 MB PNG of 400 MP — easy to craft, the *decompression bomb* of assessment finding 10 — would be 1.6 GB. The limit is on the pixels, not on the ratio: a long thin panorama of a stage front is legitimate |
| D4 | **A PDF is rendered by PDFBox 3 at 150 dpi, single page only, and only if it is not encrypted**, with the render in a **bounded 20-second timeout** on a separate thread; the rendered page is then scaled by D2. A multi-page, encrypted, broken or too slow PDF is `400`, the same answer as any other file that is not a map | ADR-007 decision 2 names PDFBox, single page, a memory limit and a render timeout. 150 dpi puts an A3 page at ~2500 px, inside D2's limit and sharp enough to read stand names; a dpi chosen from the page size would gain pixels only for pages nobody uploads. The timeout needs a thread because PDFBox's render is not interruptible from the outside; one virtual thread per upload costs nothing (Boot 4 on JDK 21+) and uploads are rare. PDFBox's own page limit is not enough: a one-page PDF can still be a decompression bomb, which is why D3's limit is applied to what it renders |
| D5 | **`413` is the size, `400` is everything else.** The 20 MB of ADR-013 L-4 is enforced by `spring.servlet.multipart.max-file-size`, whose `MaxUploadSizeExceededException` becomes `413` *The map file must be at most 20 MB.* — a detail that **names the limit**, as AC-3 asks. The domain keeps the same limit (`venue_map_version_source_size` already has it), so a caller that reaches the service another way is refused too | The contract already declares `413` for this operation and `400` for the rest. Letting the container's limit answer would send an HTML error page, not Problem Details. Checking the size only in the use case would mean buffering 2 GB before refusing it |
| D6 | **`Map.Edit` or EventAdmin**, on an event that is **open to changes** (`Draft` or `Published`, US-16 D2), with the visibility of #192 D5 checked first: a `RegularUser` member of a draft gets `404`, a member without the permission `403`, a non-member or another event's member the same `404` as an unknown event, each recorded as a refusal (US-14). The permission is read from this service's own copies — the member's `teamIds` and the teams' permission rows — never from the token (ADR-006) | The same order every write of this service uses since US-16, so the refusals of US-14 stay one rule in one place. The check itself is `Membership.isEventAdmin() || team of mine grants Map.Edit`, which is `TeamService.reads`'s shape generalised to any permission: that is why it moves into `EventReader.with(Permission)` instead of being copied a third time |
| D7 | **The version is `max(version) + 1` of that event, and the event row is locked for the transaction first** (`SELECT … FROM event WHERE event_id = … FOR UPDATE`), so two uploads of one event queue instead of racing | The table's key is `(event_id, version)`, so without it two uploads reading the same `max` both insert version *n + 1* and one dies on the primary key — and, as the review of [#249](https://github.com/tomasoliveira21/LABDSOF/pull/249) showed, **a unique violation inside a transaction cannot be retried** (Postgres aborts the whole transaction, SQLState 25P02). The lock is on the event, which every map version belongs to, so it also serialises against nothing else: no other write of this service takes it. *A sequence per event:* a sequence is not transactional, so a rolled-back upload would leave a hole in the versions the control room reads by number (US-27) |
| D8 | **The new version starts with a copy of the previous version's points** (API outline D5), inserted in the same transaction with **new `poiId`s, version 1 and the uploader as `updated_by`**, keeping the type, the name and the position; a point that was deleted is not copied | The API outline decided it. New ids, because `PointOfInterestChanged` carries one point of one map version and a shared id would make two versions of the same point indistinguishable (US-20 publishes it; #192's table already has the per-point version). Keeping the previous `updated_by` would say that someone else placed a point they never touched on this version |
| D9 | **The file is written to the volume before the row is inserted, under the name `<eventId>/<version>.png`, and is deleted again if the transaction fails** (best effort, in the use case). The directory is `farol.map.directory`, a volume of the service (API outline D6) | The row must never point at a file that is not there, which is what writing after the commit risks. The other order risks an orphan file, which costs disk and nothing else — and the name of an orphan is the version that was never stored, so nothing ever reads it. The deliberate deletion keeps even that from accumulating in the normal failure (a lost race on the lock, a broken broker) |
| D10 | **`VenueMapVersionPublished` is published through the outbox in the same transaction** (ADR-004), with `mapVersion` and `publishedAt` only (API outline §7.4), and a new `venue-map-version.published.schema.json` next to the two schemas #192 wrote. **It is the first one the product publishes**; the queue `reports.events-events` is already bound to its routing key (#212) | The outline fixes the payload: Reports only needs to know that the version exists, so a help request may point at it (US-23). The envelope, the schema file and the contract test are #192 D7's rule for the first story to publish an event type |
| D11 | **The record is `venue_map_version.uploaded_by`/`uploaded_at` and one `INFO` line** (`eventId`, the version, the source type, the source size, the actor's `userId`, the time and the correlation id) through a `MapAudit` port, as `EventAudit` and `TeamAudit` do. **No file name and no file content is logged**, and no name or e-mail (M-10) | The story's Definition of Done asks for structured logs with a correlation id. The file name carries nothing the version does not, and the content is the one thing that must never reach the log pipeline of #148 |
| D12 | **No migration.** `V1__events.sql` already holds `venue_map_version` and `point_of_interest` with the 20 MB check and the three content types | #192 D3 created both tables with this story in mind, and a `V2` that changes nothing would cost every environment a migration |

## 5. Edge-case matrix

| An EventAdmin uploads a JPEG, then a PDF | `201` each time, versions 2 and 3; every version keeps its own file | `UploadMapVersionIT` · `each upload becomes the next version and keeps the one before it` |

## 6. What the web app still needs (decision 13)

On #68: the multipart field is `file`; the answer is the new `MapVersion` (`version`, `uploadedAt`, `pointsOfInterest`); `400` means *not a map* and `413` *over 20 MB*, both with a `detail` that can be shown as it is; the image itself is read with `GET …/map-versions/{version}/image` (US-21, not implemented yet), so the back office should show the version number and the upload time until then.

## 7. Handoff and changelog

- **25 Nov 2026 · research.** Focused pass, as US-11's: ADR-007 decision 2 (the hardening list, and the pixel limit it leaves to this story — D3), the API outline's two decisions this story has to obey (D5 points, D6 volume) and its `413`, the `venue_map_version` and `point_of_interest` tables #192 already wrote, the `MapVersion`, `PointOfInterest` and `MapPosition` schemas already in `openapi.yaml`, the `venue-map-version.published` binding #212 already declared for `reports.events-events`, and the permission check `TeamService` does for `listTeams`, which D6 generalises.
- **25 Nov 2026 · implementation**, in the order of §4, with `mvn clean verify` (JDK 21) green at the end: **302 unit and 605 integration tests**, JaCoCo **1216/1219 lines (99.8 %)** and **291/292 branches (99.7 %)**, generated code included and no exclusion, PIT **201/201 mutations killed (100 %)**. No threshold lowered, no test disabled. One new dependency, `org.apache.pdfbox:pdfbox:3.0.6` (Apache 2.0), which the dependency review accepts.
- **What the gates found, and what is left uncovered.** Three gaps in the tests, all closed: a mutant of the team filter in `EventReader.granted` survived until a member of **no** team was tested on an event that *does* have a `Map.Edit` team; a boundary mutant of `MapSourceType.matches` until a file exactly as long as its signature was tested; and the `IOException` of the PNG encoding, which only a broken stream can produce, so `encode` takes the stream and the test gives it one. What stays uncovered is **one branch**: `ImageIO.write` answering `false`, which cannot happen with the writer for `"png"` the JDK always has — the same kind of gap as `EventsApplication.main`.
- **Two traps worth remembering.** `MaxUploadSizeExceededException` is already mapped by `ResponseEntityExceptionHandler`, so adding it to an `@ExceptionHandler` list makes the whole context fail to start (*Ambiguous @ExceptionHandler method mapped*); the detail is replaced by overriding `handleMaxUploadSizeExceededException` instead. And a timeout cannot be tested through a real render: the task can finish between `submit` and `get`, so the test drives `bounded` with a render that sleeps — `OutgoingEvent.payload` is a `Map.copyOf` too, whose iteration order changes from JVM to JVM, which made a `containsExactly` on it pass under Surefire and fail under PIT.
- **Open point, left on #68 and not decided here:** ADR-013 L-4 also asks the **gateway** to cap the upload at 20 MB, and the gateway has no `RequestSize` filter today. The service refuses the file itself (D5), so the limit holds end to end; what the filter would add is refusing the body before it reaches the service. The gateway is #202's, so the change belongs to its owner and is on the issue.
