## 1. Source

**Story:** as a control-room member, I want to route a request to a team, so that the right people deal with it. Persona P2.

**This PR:** `POST …/help-requests/{requestId}/route`, which sets `routedTeamId`, records it as a `routedTeamId` history entry with the member and their name, and dispatches an `Assist` field task, `Open`, to the team; a new route while that task is still `Open` cancels it and dispatches a new one. A deleted team's live tasks are cancelled and its requests go back to the control-room queue (the rule of US-16 and the domain model, which needs the field tasks this story creates). **Not in it:** the team's list of its tasks and the routed team's read of the request (US-31, #78), accepting and resolving a task (US-32, US-33), the backoffice page (the web app's owner, decision 13: what it needs is written on #76).

| # | Acceptance criterion (#76) | Tests (name starts with `US-29 AC-<n>`) |
|---|---|---|
| AC-1 | Given I open a request, then the team that handles its category is proposed by default (US-17) | `RouteRequestIT` |
| AC-2 | Given I route a request to the *Nursing* team, then it appears in that team's list with its point on the map (US-31), and the routing is recorded | `RouteRequestIT`, `HelpRequestServiceTest`, `HelpRequestTest`, `LocalCopyServiceTest` |
| AC-3 | Given a team without `HelpRequests.Respond`, then I cannot route requests to it | `RouteRequestIT`, `HelpRequestServiceTest`, `HelpRequestTest` |

AC-2's *appears in that team's list* is the field task this story stores, `Open`, for that team, with the request and its point; the list that shows it to the team's phones is US-31's (the criterion names it).

## 3. Decisions

D2 and D7 were open in the documents and were decided by the story's owner on 25 November 2026, before the work started; they are marked **Proposed, for the team's review**.

| # | Decision | Options weighed and why |
|---|---|---|
| D1 | **Route: `POST …/route` with `{ teamId }`.** The team must be a team of the request's event, not deleted, with `HelpRequests.Respond`; anything else — an unknown ID, another event's team, a deleted team, a team without the permission — is the **same `422`**, nothing written. Whether the team handles the request's category does not matter: the operator may route by hand to any team that responds (a request with no category, or none or several default teams, #149 AC-3) | The contract's `422` for a team without `HelpRequests.Respond`. *`404` for another event's team:* the request in the path exists, so a `404` would read as *request not found*; one `422` for every unusable team says nothing about teams of other events (G3). *Only the default team:* the outline's routing by hand when no team handles the category (§4.1, 15 November 2026) needs any responding team |
| D2 | **Proposed, for the team's review: routing again is allowed only while the task is `Open`.** A request can be routed while it is `Submitted` or `Seen`; routing it to another team cancels its `Open` task and dispatches a new one to that team, with one more `routedTeamId` entry. Once a member accepted the task (`OnTheWay`), and on a `Resolved` or `Closed` request, routing is `409`. Routing again to the team it is already routed to changes nothing: `200`, no entry, no new task | The documents leave re-routing open. *Re-route even an accepted task, the request back to `Seen`:* someone is already on the way, and the domain model sends a request back from `OnTheWay` only when the team is deleted. *Never re-route:* a mistake in the control room could not be undone before anybody accepts it. A request is `Submitted` or `Seen` exactly while its task, if any, is `Open` (US-32 moves both on the accept), so the status is the check |
| D3 | **The routing keeps the status** (no `Seen` on route) and moves `version` and `updatedAt`, so the live list sends the request again with its `routedTeamId`; one `routedTeamId` entry (old team ID, or null, → new team ID) with the member and their name. No event is published: the field team reads its tasks by polling (US-31, guide C5) | Domain model: *routing creates a field task and keeps the request status*. API outline §7.4 lists no routing event |
| D4 | **One live task per request**: a partial unique index on `field_task (help_request_id)` for `Open` and `Accepted`. The task is `Assist`, `Open`, for the team, dispatched at the routing's time; `acceptedBy` null. The table follows §4.1's field task document (`purpose`, `status`, `teamId`, the request, `acceptedBy`, `dispatchedAt`, `updatedAt`, `version`), with the request as its only target until US-52 adds reports | Domain model: a task targets exactly one request, one member accepts it. *A column for reports now:* no story before US-52 writes one |
| D5 | **Locks: the team's copy (`FOR SHARE`), then the request (`findForUpdate`: triage, then request), then its task.** The team deletion takes the same order: its `TeamChanged` locks the team's copy, then each request routed to it, then that request's task | A route reading a team as it is being deleted would dispatch a task to a deleted team after the deletion swept its tasks; holding the team's row until the routing commits makes the deletion wait for it (or the route wait for the deletion, and then read it deleted: `422`). One order for both, so they never deadlock |
| D6 | **A deleted team** (`TeamChanged` with `deleted: true`, applied as newer): each request routed to it that is not `Resolved` or `Closed` gets `routedTeamId` null, `OnTheWay` becomes `Seen`, `version` and `updatedAt` move (back in the live list, for the control room to route again), and its live task becomes `Cancelled`. No history entry: only a member's change is one (US-28 D6), and the contract says `actorUserId` is never empty. A stale or repeated `TeamChanged` does nothing | US-16 *the requests routed to it go back to the control room queue*; domain model `Open` or `Accepted` → `Cancelled`, `OnTheWay → Seen`; API outline §7.4. A team that only loses `HelpRequests.Respond` keeps its tasks: no document says otherwise |
| D7 | **Proposed, for the team's review: closing a request cancels its live task** (`Open` or `Accepted` → `Cancelled`) in the same transaction, so a closed request leaves the team's list too. Built in this PR once US-30 (PR #252) entered `main` (D7 was written before; this PR was merged second) | US-30 left the decision to this story. *Leave the task and let US-31 hide tasks of closed requests:* a task would stay `Open` or `Accepted` for ever on a finished case. *Stack this PR on #252:* the plan avoids stacks unless the code is needed, and only this one line of behaviour is |
| D8 | **Who may act:** `HelpRequests.Triage` in the request's event (`403` without it); a non-member, a removed member, a member of another event, a valid token without `sub`, a request of another event or unknown gets `404` with the same body; every bad token gets `401`; a malformed ID, a missing or null `teamId`, a malformed body or an unknown field gets `400` | API outline §4, US-28 D7; G3. The request's `404` comes before the team's `422`, and the team's `422` before the status's `409` (the body is checked before the state, as US-30's G8 review set) |
| D9 | **The routing is logged at `INFO` with the request ID and the old and new team IDs**, never the description or the user; it answers `200` with the control-room view after it, default team included | US-28 D8, D9 and US-34 D4 |
