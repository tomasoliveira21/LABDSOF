## 1. Source

**Story:** as a control-room member, I want to accept or change the AI suggestion, so that I stay in control of the decision. Persona P2.

**This PR:** `POST …/help-requests/{requestId}/accept-suggestion`; `PATCH …/help-requests/{requestId}` for the category and the priority (the transition to `Changed`); every decision recorded with who, when, and the old and new value; the counter of accepted and changed suggestions. **Not in it:** the default team that follows from the category (#81 AC-2, after US-17 #66); the status changes, `/acknowledge` and the `GET …/history` endpoint of US-28 (#75), which reads the records this story writes; the backoffice page (the web app's owner, decision 13: what it needs is written on #82).

| # | Acceptance criterion (#82) | Tests (name starts with `US-35 AC-<n>`) |
|---|---|---|
| AC-1 | Given I accept the suggestion, then its values become the request's values and the change is recorded as mine (`Accepted`) | `TriageDecisionIT`, `HelpRequestServiceTest`, `HelpRequestTest`, `MicrometerTriageMetricsTest` |
| AC-2 | Given I already set a category or priority, when a suggestion arrives, then my values are not changed (NFR-22); and changing a suggestion records `Changed` | `TriageDecisionIT`, `HelpRequestServiceTest`, `HelpRequestTest` |

The model's offline quality gate still fails (#224, #227): the suggestion is not release evidence, and the operator's decision is what counts. These tests use requests whose suggestion is written by the test, not by a model.

## 3. Decisions

Decisions the documents leave open are marked **Proposed, for the team's review**.

| # | Decision | Options weighed and why |
|---|---|---|
| D1 | **Accept: `POST …/accept-suggestion`, no body**, only while the triage is `Suggested`: the request's category and priority become the suggested ones, the triage becomes `Accepted`, and the suggestion (category, priority, reason) stays visible. Anything else is `409` (no suggestion yet, `NotTriaged`, already `Accepted` or `Changed`) | API outline §4 and the planned contract (`409 when there is no suggestion or a member already set the values`); domain model: `Suggested → Accepted` |
| D2 | **Proposed, for the team's review: change through `PATCH …/help-requests/{requestId}`** (`{ category, priority }`, either or both, at least one), which the contract planned for US-28. Any value a member sets makes the triage `Changed`, from `Suggested`, `NotTriaged`, `Accepted`, and also from `Pending` (a member decides before the AI answers). A `PATCH` with the suggested values is still `Changed`: accepting is the explicit action. A `PATCH` with the values the request already has writes nothing, whatever the triage state (so an `Accepted` triage stays `Accepted`; G8 review). A field left out keeps its value; a JSON `null` is refused (`400`), as the contract's schema says | The domain model lists `Suggested → Changed` and `NotTriaged → Changed`; `Pending → Changed` and `Accepted → Changed` are needed for AC-2 (*I already set a category or priority, when a suggestion arrives*) and for a member who corrects an accepted value. Options: a new `…/change-suggestion` action (not in the API outline), or the `PATCH` the outline already has (chosen); US-28 adds the status to it later. The derived `NotTriaged` reason is stored with `Changed`, so the read still says why there was no suggestion |
| D3 | **Proposed, for the team's review: every decision is recorded in `help_request_change`** (Flyway `V3`), one row per field that changed (`category`, `priority`, `triage`), with the old and new value, the member's token `sub` and the time, in the same transaction; the request's `version` goes up by one and its `updated_at` moves, so the live list shows it | AC-1 *recorded as mine*; API outline §4 (`PATCH` recorded with who, when, old and new value); the field names and values are those of the planned history entry in `openapi.yaml`, so US-28's `GET …/history` reads these rows as they are. Options: two columns `decided_by`/`decided_at` on the triage (loses the old values and needs a table later anyway) or the history table now (chosen) |
| D4 | **The member's write locks the triage, then the request (`SELECT … FOR UPDATE`), and decides on what it reads there**; the triage worker's save is one conditional `UPDATE` of the triage on `Pending` without a reason, then of the request, so it waits for the member's transaction and then finds a decided triage and writes nothing. Both take the two rows in the same order, or each could wait on the other (deadlock; G8 review). Two accepts at the same time: the second reads `Accepted` and gets `409` | NFR-22 and the runtime contract (*Completion*: a result never overwrites an operator decision; required scenario *operator edit during inference*). The suggestion is never written to the request's own category or priority (US-34 D6), so only the triage state can race |
| D5 | **Who may decide:** `HelpRequests.Triage` in the request's event (`403` without it); a non-member, a removed member, a member of another event, or a request of another event or unknown gets `404` with the same body; every bad token gets `401`; a malformed ID, malformed JSON, an unknown field, an unknown category or priority, or a body with neither field gets `400` | API outline §4 and the matrix of the live list (US-26); G3 |
| D6 | **Proposed, for the team's review: counter `farol.triage.decision{decision}`** (`Accepted` or `Changed`), counted once per request, at the first member decision on a stored suggestion (`Suggested → Accepted` or `Changed`), after the commit, so a decision rolled back is never counted (G8 review). A member's triage of a request without a suggestion is not counted here: `farol.triage.fallback` already counts that request (US-36 D7) | The observability research (I3 item 3) asks for accepted and changed suggestions on the dashboard, and the reason review of #149 needs the share of suggestions members change. The name follows `farol.triage.*` of US-36 |
| D7 | **The default team is not set**: `defaultTeamId` stays null after an accept | API outline §4 says the default team follows from the category; that rule needs each team's categories from Events (#81 AC-2, US-17 #66), which is not built |
| D8 | **Each decision is logged at `INFO` with the request ID and the triage state before and after**, never the description, the reason or the user | ADR-005 decision 5 (metadata, not bodies). The token `sub` is in the database record, not in the log |
| D9 | **The response is the control-room view of the request after the decision** (`200`) | The planned contract (`ControlRoomView`), so the web app needs no second read |

| Case | Expected | Test |
|---|---|---|
