## 1. Source

**Story:** as a control-room member, I want requests to keep arriving when the AI is down, so that no one is left without help (scenario D1). Persona P2.

**This PR:** the circuit breaker on the AI call (J1 values), `GET /api/v1/events/{eventId}/triage-status` for the web app's banner, the fallback counter and its log line, and the SC5 integration test with the AI stopped, slow, failing or invalid. **Already delivered by US-34 (#229) and US-26 (#73), and checked again here:** a request is saved and listed at once, never waits for the AI, and reads `NotTriaged` with its reason when no valid suggestion is stored. **Not in it:** setting the category and priority by hand (US-28, #75: no `PATCH` exists yet, so the test cannot set them); the banner itself (the web app's owner, decision 13: what the page needs is written on #83); the WireMock container of the demo (guide J4, `architecture.md` §9.3); the one-hour useful-triage gauges of the dashboard (SC3, #149).

| # | Acceptance criterion (#83) | Tests (name starts with `US-36 AC-<n>`) |
|---|---|---|
| AC-1 | Given the AI does not answer within 30 s, or answers with an error or invalid data, then the request is shown with its description, no category and no priority, marked `NotTriaged`, in order of arrival, for the operator to set by hand (SC5) | `TriageFallbackIT`, `TriageServiceTest` |
| AC-2 | Given the AI provider is down, then the back office can tell that triage is unavailable (`GET …/triage-status`, polled by the web app for its banner) | `TriageFallbackIT`, `TriageStatusIT`, `TriageServiceTest`, `ResilienceTriageCircuitTest`, `HelpRequestServiceTest` |
| AC-3 | Given a fallback happens, then it is logged with its reason and counted in the fallback-rate metric | `TriageFallbackIT`, `TriageServiceTest`, `MicrometerTriageMetricsTest` |

The model's offline quality gate still fails (#224, #227): the suggestion is not release evidence, and operator triage is the fallback. SC5 is about the fallback, so it is measured with the AI off or broken and does not depend on that gate.

## 3. Decisions

Decisions the documents leave open are marked **Proposed, for the team's review**.

| # | Decision | Options weighed and why |
|---|---|---|
| D1 | **Circuit breaker with Resilience4j 2.4** (`resilience4j-spring-boot4`), instance `ai-provider`, configured in `application.properties` with the J1 values: count-based window of 10 calls, at least 4, opens at ≥ 50 % failed or ≥ 50 % slow (> 16 s) calls, open 30 s, one probe in half-open | Fixed by J1 (`architecture.md` §9.1, accepted on 27 October 2026) and the runtime contract. Used programmatically (no annotations, no AOP), from an out adapter, as J1 says |
| D2 | **What the circuit records**: one call per request that reached the model. `Timeout`, `ProviderError` and `InvalidOutput` are failures; a suggestion or an abstention is a success; every call carries its duration, so a slow success counts as slow. A request not sent (AI not configured, admission, circuit open) records nothing | `architecture.md` §9.2 *Detected*: timeout, connection error, provider error or invalid output. An abstention is a valid answer of a working provider. Invalid output is validated in the domain (US-34 D4), so the service reports the outcome to the circuit, not the adapter |
| D3 | **While the circuit is open or half-open, a request is `Unavailable` without a call** | API outline §4.1: `Unavailable` is *the AI was not called because the circuit was open or the request could not start in time* |
| D4 | **Proposed, for the team's review: `GET …/triage-status` answers `available: true` only when an AI is configured and the circuit is closed**; otherwise `available: false` with `reason` `Unavailable` (no AI configured, or a circuit opened by slow calls that all answered) or the reason of the last failed call since the last successful one (`Timeout`, `ProviderError`, `InvalidOutput`), and `checkedAt` the server time. One AI serves every event, so the answer is the same for every event; the event in the path decides only who may read it. After the 30 s open time the status stays unavailable until the next request's probe succeeds: Resilience4j moves to half-open only when a call is attempted | `architecture.md` §9.2 *Degraded state*: open or half-open → banner; *Recovery*: the banner disappears after a successful trial call. One fallback alone only labels its request. The contract (`openapi.yaml`, planned since #194) has `available`, `reason` and `checkedAt` but does not say which reason; the last failure tells the operator why. Options: always `Unavailable` (says less), or the last failure (chosen) |
| D5 | **Who reads the status**: `HelpRequests.Triage` in the event (403 without it); a non-member, a removed member or a member of another event gets 404; every bad token gets 401 | API outline §4 (`Requires HelpRequests.Triage`) and the rules of the live list (US-26 AC-2), so the banner shows to the same people as the list |
| D6 | **Proposed, for the team's review: the web app polls the status with the live list, every 2 s while the page is visible** | US-26 D7. The circuit opens after the 4th failed call and stays open at least 30 s, so a 2 s poll shows the banner within about 2 s of the change |
| D7 | **Fallback counter `farol.triage.fallback{reason}`** (Micrometer, name from `architecture.md` §9.2), one per request the worker leaves to the operator: every `NotTriaged` reason (`Timeout`, `ProviderError`, `InvalidOutput`, `Abstained`, `Unavailable`); a result discarded after the deadline counts as `Timeout`, as the request then reads, but only when the AI was called (once per request, by admission): a message handled only after its deadline can be delivered again and counts nothing, like a message that never arrived (G8 review). **Proposed, for the team's review:** a second counter `farol.triage.suggested` for the stored suggestions, so the fallback rate is `fallback / (fallback + suggested)`. Resilience4j adds `resilience4j.circuitbreaker.state{name=ai-provider}` | AC-3 and features.md §3.1 D1 *Recorded*. A rate needs a denominator; the documents name only the fallback metric. A request already triaged (redelivered message) or deleted counts nothing, so a request counts once. A request whose message never reached the worker (broker down) reads `Timeout` at 30 s without a count: the outbox-age alert of ADR-012 covers that case |
| D8 | **Proposed, for the team's review: Micrometer through `spring-boot-starter-actuator`, with no actuator endpoint added on the API port** | The meter registry needs the actuator. Its default web exposure is `health` only, behind the token of the API chain; the Prometheus endpoint on the private management port comes with #148 (PR #231), which adds the same dependency |
| D9 | **Each fallback is logged at `WARN` with the request ID, the reason and the time spent**, never the description or the model's text | AC-3 and ADR-005 decision 5 (metadata, not bodies). `HelpRequestSubmitted` carries no correlation ID on this branch (US-34 D12); #148 (PR #231) adds it to the consumer's MDC, so the line gets it once both are merged |
| D10 | **The SC5 test is a Reports integration test with the AI stub in place of WireMock**: the AI stopped (connection refused), a reply slower than the timeout, HTTP 503, a dropped connection and an invalid body; 20 requests per case | `architecture.md` §9.2 *Automated test*. The stub plays WireMock's part in the test (US-34 D10), so no new container is needed for it; WireMock stays for the demo (guide J4). The response timeout is 2 s in the test (as `TriageIT`) and the open time is 5 s, so the test does not wait 30 s (5 s, not less, so the 16 requests after the 4th are all handled while the circuit is open); the production values are checked by `ResilienceTriageCircuitTest` |
| D11 | **Recovery**: after the open time, one probe goes to the AI; a success closes the circuit and the status reads available again; requests whose deadline passed while the circuit was open stay `NotTriaged` | `architecture.md` §9.2 *Recovery*, the runtime contract (*Completion*). The deadline is never reset (US-34 D6) |
| D12 | **The smoke test checks the status through the gateway on the default stack (no `ai` service)**: no token → 401, a user who is not a member of the event → 404 | The plan of this work asks for a smoke step with no `ollama` service. The default stack has no event membership to read the status with a 200; the IT covers the 200 with no AI configured (`TriageStatusIT`) |

## 5. Edge-case matrix

| Case | Expected | Test |
|---|---|---|
| AI stopped (connection refused), 20 requests | 100 % listed for the control room within 30 s in order of arrival, with their description, no category or priority, `NotTriaged` (`ProviderError`, then `Unavailable` once the circuit opens) | `TriageFallbackIT` · `US-36 AC-1 with the AI stopped every request reaches the operator in order of arrival` |
| Reply slower than the timeout, HTTP 503, dropped connection, invalid body; 20 requests each | 100 % `NotTriaged` within 30 s with the reason; the circuit opens after 4 calls and the AI gets no more calls | `TriageFallbackIT` · `US-36 AC-1 a slow, failing or invalid AI leaves every request to the operator` |
| Circuit open or half-open | `Unavailable`, no call | `TriageServiceTest` · `US-36 AC-2 while the circuit is open the AI is not called` |
| What the circuit records | `Timeout`, `ProviderError`, `InvalidOutput` → failure with the duration; suggestion or abstention → success with the duration; nothing when the AI was not called | `TriageServiceTest` · `US-36 AC-2 the circuit records each call's outcome and duration` |
| Interrupted call (shutdown), or an `Error` during the call | The circuit's permission is released, nothing recorded, the exception propagates (message redelivered) | `TriageServiceTest` · `US-36 AC-2 an interrupted call releases the circuit` |
| Last failure after a success | Cleared: a circuit opened later by slow calls reads `Unavailable`, never an old reason or null | `ResilienceTriageCircuitTest` · `US-36 AC-2 a successful call clears the last failure`; `TriageServiceTest` · `US-36 AC-2 the status says whether the AI can be called and why not` |
| Circuit values | Production properties: window 10, minimum 4, 50 % failed, 50 % slow over 16 s, open 30 s, one probe; it opens after 4 calls with 2 failed and closes after a successful probe | `ResilienceTriageCircuitTest` · `US-36 AC-2 the circuit has the J1 values`, `US-36 AC-2 the circuit opens after 4 calls with half failed and closes after a successful probe` |
| Slow calls | 4 successful calls over 16 s open the circuit | `ResilienceTriageCircuitTest` · `US-36 AC-2 slow calls open the circuit` |
| Status: AI not configured / circuit closed / open | `available: false` `Unavailable` / `available: true` without reason / `available: false` with the last failure's reason | `TriageServiceTest` · `US-36 AC-2 the status says whether the AI can be called and why not`; `TriageStatusIT` · `US-36 AC-2 the control room reads the triage status` |
| Status while the AI is down, then after recovery | Unavailable while open; after the open time a request is triaged by the probe, the circuit closes, the status reads available, the requests missed while open stay `NotTriaged` | `TriageFallbackIT` · `US-36 AC-2 the status reads unavailable while the AI is down and available after a successful probe` |
| Status: member without `HelpRequests.Triage` | 403 | `HelpRequestServiceTest` · `US-36 AC-2 only the control room reads the triage status`; `TriageStatusIT` · `US-36 AC-2 a member without HelpRequests.Triage gets 403` |
| Status: non-member, removed member, member of another event | 404 | `TriageStatusIT` · `US-36 AC-2 a non-member, a removed member or a member of another event gets 404` |
| Status: no, expired, wrong-signature, wrong-issuer, wrong-audience, malformed token | 401 | `TriageStatusIT` · `US-36 AC-2 every bad token gets 401` |
| Status: malformed event ID | 400 | `TriageStatusIT` · `US-36 AC-2 a malformed event id is rejected` |
| Fallback counted | One count per request left to the operator, by reason; a late result of a call counts `Timeout`; a suggestion counts `suggested`; a redelivered or unknown request, or a message handled only after its deadline (delivered twice), counts nothing | `TriageServiceTest` · `US-36 AC-3 every fallback is counted once with its reason`; `MicrometerTriageMetricsTest` · `US-36 AC-3 the counters have the metric names and the reason tag`; `TriageFallbackIT` · `US-36 AC-3 every fallback is counted by reason` |
| Fallback logged | `WARN` line with the request ID, the reason and the time; never the description | `TriageServiceTest` · `US-36 AC-3 each fallback is logged with its reason and without the description` |
| Default stack, no `ai` service | Status through the gateway: 401 without a token, 404 for a non-member | `reports_smoke.py` (CI step *Reports validates Keycloak tokens*) |
