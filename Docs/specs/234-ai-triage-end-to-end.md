## 3. Decisions

| # | Decision | Why |
|---|---|---|
| D1 | **Arrival profile: one help request every 30 s, on a fixed schedule** (open model: the next request is sent at its time whatever happened to the previous one), the 72 holdout cases in file order, 36 minutes per run. *Proposed, for the team's review* | NFR-03 and the runtime contract fix the deadline and the capacity (one model call at a time, a bounded queue) but no arrival rate. The only stated rates are the Sprint C peak L3 (1 help request per second, with WireMock in place of the AI, `architecture.md` §10.1) and *a few help requests per minute* at night (§9.1, J1). One local model answers in about 12 s (#227), so 1 per second would only measure the queue, which L3 does not ask of the real model. One every 30 s is the rate the plan of this work names when no source states one; it keeps at most one request waiting |
| D2 | **Participants and fixture**: Rita, Sofia, Inês and Nuno submit in turn (each one every 2 minutes, within the planned limit of 5 help requests per 10 minutes per account, API outline §1, not enforced yet: #190), each with a fresh Keycloak token from the PKCE login, through the gateway (`127.0.0.1:8080`). Miguel is in a `Control room` team with `HelpRequests.Triage` and polls `GET …/help-requests` and `GET …/triage-status` every 2 s (L3's operator). Their memberships and the team are written into Reports' local copies (`membership_copy`, `team_copy`) with SQL before the run, one new event per run | Joining an event (US-12) and teams (US-18) answer `501` in Auth & Users, and Events publishes no `TeamChanged` yet, so the copies cannot come from their producers. The fixture is the same rows their messages would write (`LocalCopyListener`); the measured path, submission to stored suggestion, is the real one |
| D3 | **SC3 measurement**: per request, `stored_at − submitted_at`, both Reports' own clock (`help_request.submitted_at` at the submission, `triage_suggestion.updated_at` written by the triage worker when it stores the outcome), read in one snapshot after the last deadline. Valid within 30 s: state `Suggested` with a category and a priority stored ≤ 30 s after submission. Headline: the **66 non-abstention cases** (ADR-005 offline definition, target ≥ 95 %); also the NFR-03 operational count over all 72, where the 6 expected abstentions are misses. A request still `Pending` with no reason after its deadline counts as `Timeout` (as the read derives it); an abstention, an error, an invalid output and a late result are misses. Also: p50, p95 (nearest rank), max of the end-to-end time of the stored suggestions; fallbacks by reason; the worker's model time from its log line; the operator's view time | I2 counts the useful-triage SLI from the persisted submission and outcome timestamps, never from success counters; the timer of NFR-03 is the worker's clock at storage. No new metric or gauge is added here: the `farol_triage_window_*` gauges the dashboard of #148 expects stay a known limit (§6) |
| D4 | **SC5 measurement**: the same 72 submissions with the same profile, `FAROL_AI_URL` still set and the `ai` container stopped. Pass, fixed before the run: **every** request appears in the operator's list and reads `NotTriaged` with a reason at a poll no later than 32 s after it was sent (the 30 s deadline plus one 2 s poll), and the list is in order of arrival | SC5 asks 100 % shown to the operator; US-36 AC-1 the description, no category or priority, `NotTriaged`, order of arrival |
| D5 | **Runtime as #224 and #227**: the Compose `ai` service (`ollama/ollama:0.40.16` by digest, the same settings), `qwen3:4b` copied from the #224 model volume and checked by digest, prompt v8 as packaged in Reports (`TriagePackageIT`), Reports' warm-up; the run starts once `ollama ps` shows the model loaded. Container memory from cgroup `memory.peak` after the SC3 run | Keeps the model and prompt of the offline runs, so the end-to-end numbers add the system around them and nothing else |
| D6 | **Label-review table**: `label_review.py` writes `label-review/labels.md` from `cases.jsonl`, `dev-extra.jsonl` and `holdout.jsonl`: urgent references (minimum `High` or `Critical`) first, then expected abstentions, then the rest, each group by split (holdout, test, dev) and ID; one line per case with ID, split, text, category, minimum priority, abstain and tags. No model output, so the reviewer is not anchored. A guide (`label-review/README.md`) gives the rubric (`features.md` §4.2 and §5.3, the minimum-priority rule) and how to answer: a review comment on the line of each label to change, with the new value and why, and a sentence in the review saying which cases were reviewed | Plan of #149 part 4; one line per case lets a GitHub review comment point at one case. The author of this spec has not read the holdout texts (spec 227 D2) and checks the table by script only |

## 5. Edge-case matrix

| Case | Expected | Check |
|---|---|---|
| A stored suggestion more than 30 s after submission | Not valid | `234 AC-2 valid within 30 s counts only stored suggestions` |
| An abstention, or a request still `Pending` after its deadline | Miss; the pending one counted as `Timeout` | `234 AC-2 an abstention and a request still pending count as misses` |
| A submission refused (not `201`) | Row kept with its status, counted as not shown and not valid | `234 AC-2 SC5 passes only when every request is shown and NotTriaged in time`, `234 AC-2 valid within 30 s counts only stored suggestions` |
| A row missing or repeated for a holdout case | `--verify` fails | `234 AC-2 the rows hold one line per holdout case` |
| A summary edited by hand | `--verify` fails | `234 AC-2 a summary is recomputed from its rows` |
| The case file changed after the manifest, or no driver commit named | `--verify` fails | `234 AC-1 the manifest hashes the case file and names the driver commit` |
| SC5: one request shown late, or never `NotTriaged`, or out of order | SC5 fails | `234 AC-2 SC5 passes only when every request is shown and NotTriaged in time` |
| A case text with a pipe or a line break | Escaped, the table keeps one line per case | `234 AC-3 a pipe or newline in a text cannot break a line` |
| The table edited by hand | `--check` fails | `234 AC-3 the table is what the script writes` |
