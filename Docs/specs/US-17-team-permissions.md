## 1. Source

**Story:** as an **EventAdmin** (persona P3 · Sofia), I want to set the permissions and help categories of each team, so that each team can do exactly what its job needs.

**This PR:** `PUT /api/v1/events/{eventId}/teams/{teamId}/permissions` — the last operation of the *Teams* tag — with the report types of `Reports.Review`, the record of who changed them and when, and the structured log line of the change. **Not in it:** the help categories, which [US-16](US-16-teams.md) D1 already ships in `PATCH …/teams/{teamId}` (AC-3 below says what is left to check here); the back-office page (the web app's, decision 13: what it needs is on #66); routing a help request to the default team of a category (US-29, #76) and the AI suggestion that fills the category (US-34, US-35), both in Reports; putting members in a team (US-18, #67, Auth & Users).

## 3. Decisions

| # | Decision | Options weighed and why |
|---|---|---|
| D1 | **`PUT` replaces the whole set in one transaction:** the team's `team_permission` rows are deleted and the sent ones inserted, `team.version` is bumped, and **one** `TeamChanged` carries the new set. An empty array is valid and takes every permission away (that is how AC-4's *remove a permission* is done) | The contract and API outline §3 say *replace*, and `TeamChanged` carries full state (§7.4), so a partial update would need a second shape. *`PATCH` with add and remove lists:* not in the contract, and two calls would publish two versions for one intention |
| D2 | **Repeating the same set still bumps the version and publishes**, exactly as a rename to the same name does (US-16) | AC-4 asks for the change to be *recorded with my name and the time*: each call is a decision by an EventAdmin and is recorded. Comparing with the stored set to skip a no-op would save a version but hide that someone re-confirmed the permissions, and the consumers already ignore anything that is not strictly newer |
| D3 | **`Reports.Review` with no report types is accepted** and means *reviews nothing yet*; every other permission with report types is `400` | API outline §4 gives `Reports.Review` **for its type** on each report operation, so a Review with no type simply matches no report. Refusing it would block the normal way of filling a form (pick the permission, then the types) and would need a `422` the contract does not declare. `team_permission`'s check and `team.changed.schema.json` already forbid the other direction, and the domain repeats it |
| D4 | **A repeated permission, or a repeated report type inside one permission, is `400`** (`maxItems: 8` on the array is already in the contract) | `team_permission`'s primary key is `(team_id, permission)`, so a repeated permission cannot be stored, and `uniqueItems` in the published schema forbids a repeated report type. As in US-16 D7, the contract keeps plain arrays and the **domain** refuses the duplicate, because `uniqueItems` would make the generator read a `Set` and deduplicate it silently |
| D5 | **Several teams may handle the same category, and several may review the same report type: not refused** | *Which team is the default when two teams handle the same category* is an **open product decision** (domain model). Refusing the second team would close it by accident, in the wrong place, and would stop a legitimate set-up (two nursing posts). Reports picks the default team and answers `defaultTeamId: null` when no team handles the category (API outline, 15 November 2026). **Flagged on the pull request and on #66 for the Product Owner**; US-16 already allows it for the categories |
| D6 | **The record of AC-4 is `team.updated_by` and `team.updated_at`, the published `TeamChanged`, and one `INFO` log line** (`teamId`, the permissions after the change, the actor's `userId`, the time and the request's correlation id), through a `TeamAudit` port as `AccessAudit` already does. **No name is stored or logged:** the `userId` is the token's pseudonymous `sub` (M-10), and the web app resolves the name | The contract has no teams-audit path, and inventing one is out of scope. *A new audit table:* nothing reads it yet; `updated_by`/`updated_at` plus the event already answer *who and when*, and the log line makes it visible in the observability stack (#148). The permission list is not personal data, so it may be logged |
| D7 | **`409` while the event is `Suspended` or `Closed`**, as US-16 D2, with the same detail; one `409` is added to `PUT` in `openapi.yaml` | One rule for every team write. The same open point goes to the Product Owner once, in US-16 |
| D8 | **"At the member's next action" needs nothing in Events:** no permission is cached, every use case reads `team_permission` through its port, so a removed permission stops granting on the next request after the commit. In the other services it is their copy of `TeamChanged` | ADR-006: each service decides from its own local copies. Events' own check (US-16 D4, `GET …/teams`) is the one that must be seen to change, and it is tested |

## 6. Handoff and changelog

- **21 Nov 2026 · research.** Short, focused pass: the shared ground (tables, contract, `TeamChanged`, authorisation, the gates and the test shape) was covered by [US-16](US-16-teams.md)'s research the same day, so only what is specific to US-17 was looked at — how Reports uses `reportTypes` (`Reports.Review` **for its type**, API outline §4 and `reports`' `LocalCopyListener`, which reads a missing `reportTypes` as empty), what *recorded with my name and the time* can mean with no audit path in the contract and no names in the logs (D6), and the state of the open product decision on the default team (D5). Also checked: the report type codes are in **no** other document or contract, so they stay Events' proposal (#192 D6) and the report stories have to adopt the same list.
- **21 Nov 2026 · implementation**, in the order of §4, with `mvn clean verify` (JDK 21) green at the end: **175 unit and 548 integration tests**, JaCoCo **845/847 lines (99.8 %)** — the two missed are `EventsApplication.main` — and **224/224 branches (100 %)**, generated code included and no exclusion, PIT **125/125 mutations killed (100 %)**. No threshold lowered, no test disabled.
- **One failure on the way, both mistakes in the new assertions, not in the code:** the log line's field is `correlationId` (not `correlation_id`), and the report types read in the order of their fixed list (`[NoWater, Hazard]`), not in the order the caller sent. The line itself was already right.
- **Known limit of D6's log line:** it is written inside the transaction, just after the outbox row, so a failure at **commit** would leave a line about a change that did not land. The stored record (`updated_by`, `updated_at`) and the published event are rolled back together, which is what the consumers and the back office read; moving the line after the commit would need a transaction synchronisation and would lose the request's MDC. Revisit if #148's dashboards ever count these lines as changes.
- **Not reproduced locally:** the Compose smoke run of `ci.yml`. The smoke cannot reach a team (no event can be created before US-06), so this story adds no step to it; #65's branch fixes the one check that US-16 had made false, and CI runs it.
- **Left for later stories:** US-29 (#76) routes a help request to the default team of its category and is where D5's tie-break will be felt first; US-18 (#67) puts members in a team, so a member only gets these permissions once that lands; US-50 to US-53 are where `Reports.Review`'s report types start to matter, and they must use the codes this story stores.
- **Open points for the Product Owner** (also on the pull request and on #66): (1) **D5**, whether two teams may handle the same category or review the same report type — allowed here, because refusing it would close the open *default team* decision by accident; (2) **US-16 D2**, whether a suspended or closed event may still have its teams changed — refused here with `409`; (3) the report type codes are still Events' proposal; (4) `Docs/Product/mockups/` still has no back-office team screens, which the Definition of Ready asks for.
