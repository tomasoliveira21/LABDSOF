## 1. Source

**Story:** as an **EventAdmin** (persona P3 · Sofia), I want to publish my event, so that participants can find it.

**This PR:** `POST /api/v1/events/{eventId}/publish` — the last operation of the *Events* tag that Sprint B needs — with the join code it generates, the `EventChanged` it publishes (**the first one Events ever publishes**) and the log line that records it. **Not in it:** creating the draft (US-06, #61) and listing events (US-07); suspending, reactivating and closing (US-09, #91; US-13, #93); editing (US-10, #92); joining by the link or the QR code, which is Auth & Users' `POST …/members/me` (US-12, #63); drawing the QR code, which is the web app's (decision 13: what it needs is on #62).

| # | Acceptance criterion | Tests (name starts with `US-11 AC-1`) |
|---|---|---|
| AC-1 | Given my event is a draft, when I publish it, then participants can open it, and its QR code and link are generated | `EventTest`, `EventServiceTest`, `PublishEventIT`, `JdbcEventsIT`, `EventContractIT` (*participants can open it*: the `RegularUser` who got `404` on the draft reads the event, with its join link, right after the publish — `PublishEventIT`; *its QR code and link are generated*: the join code is created here and answered as the `joinLink` the QR code encodes, the web app drawing the code itself) |

## 3. Decisions

| # | Decision | Options weighed and why |
|---|---|---|
| D1 | **The join code is 160 bits from `SecureRandom`, Base64 URL-safe without padding (27 characters)**, made behind a `JoinCodes` port so the use case is tested with a fixed code. The `event_join_code_unique` index is the only check, and a collision (2⁻¹⁶⁰ per publish) is **left to roll the transaction back**: the request ends in `500` with nothing written, and the next one gets another code | *Retrying the code in the same transaction* (what this branch first did, [review of #249](https://github.com/tomasoliveira21/LABDSOF/pull/249)): against Postgres it cannot work — the unique violation aborts the transaction of `publish`, so the retry's `UPDATE` fails with *current transaction is aborted* (SQLState 25P02) and the request ends in `500` anyway; the driver has no `autosave`, so only an explicit savepoint around the `UPDATE` would rescue it, which is machinery for an outcome no event will ever see. *A short human code (6–8 characters):* nothing in the contract types a code — Auth & Users joins by `eventId` alone (§2) — so shortness buys nothing and makes the link guessable. *Derived from the `eventId`:* the link would carry no secret at all, and a future check would be worthless. *A `UUID`:* 122 bits is enough, but a second uuid in the link reads as an identifier and invites being treated as one. Base64 URL-safe needs no percent-encoding, so the link in the QR code is the string itself |
| D2 | **Only a `Draft` publishes.** Every other status is `409` *This event is not a draft.*, and a second publish of the same event is `409` too: the operation is **not** idempotent | The acceptance criterion is *given my event is a draft*, the state machine of the domain model has the one `Draft` → `Published` edge, and the contract already declares the `409`. *Answering `200` again:* it would have to choose between re-issuing the join code (breaking every link and QR code already printed, and `event_join_code_once_published` with it) and keeping it while reporting a change that did not happen; a double-click that gets `409` loses nothing, because the first answer already carries the event |
| D3 | **An EventAdmin of the event, and the visibility of #192 D5 is checked first:** a `RegularUser` member of a draft gets `404` (a draft is not visible to participants), not `403`; a `RegularUser` of a published event gets `403`; a non-member, a member of another event and a `FarolAdmin` who is not a member get the same `404` as an unknown event, each recorded as a refusal (US-14, #192 D8) | Exactly the order `TeamService` already uses for every team write, so the refusals of US-14 stay one rule in one place. Checking the role first would tell a participant that a draft event exists |
| D4 | **The write carries the status *and* the version it read:** `WHERE status = 'Draft' AND version = :version - 1`. A miss is read back in the same transaction: a row that is still a draft lost a race and is `409` *This event changed meanwhile; read it again.*; a row that is no longer a draft is `409` *This event is not a draft.*; no row at all is the `404` of an unknown event. Nothing is written, published or logged in any of the three | Decision 3 of 21 November 2026, now the rule for every write of this service: without the version, two publishes starting from the same read both commit and publish **two `EventChanged` carrying one version**, and a consumer that applies only a strictly newer version would keep whichever arrived first. The status in the same `WHERE` makes the one transition atomic, so no event gets two join codes |
| D5 | **`EventChanged` is published here for the first time**, through the outbox in the business transaction (ADR-004), with `name`, `organiserName`, `dates`, `status` and `version` — **no description and no join code** (`event.changed.schema.json`). The payload helper that `EventContractIT` has carried since #192 becomes the service's own `EventEvents.changed` factory, which is what #192 D7 asked of the first story to publish it | The schema and API outline §7.4 fix the payload; the consumers (Auth & Users to accept joins, Reports and Transports to refuse a suspended or closed event, Badges for the event's name) need no more. Leaving the helper in the test would mean the factory and the contract test could drift, which is the one thing that test exists to stop |
| D6 | **The answer is the whole event, with its `joinLink`, exactly as `GET /events/{eventId}` returns it** — the same mapper, the same relative route `/join/{eventId}?code=…` of #192, which the web app makes absolute for the QR code | The contract's `200` is an `Event`, and the back office needs the link right after the publish; a second `GET` would be a round trip for data the write already has. The route stays relative because only the web app knows its own origin |
| D7 | **The record is `event.updated_by` and `event.updated_at`, the published `EventChanged`, and one `INFO` line** (`eventId`, the new status, the new version, the actor's `userId`, the time and the request's correlation id) through an `EventAudit` port, as `TeamAudit` does for US-17 D6. **The join code is never logged** and no name or e-mail is (M-10) | The story's Definition of Done asks for structured logs with a correlation id for the new behaviour. The join code is the one value in the row that should not spread through the log pipeline of #148, and nothing in a log line needs it |
| D8 | **No migration.** `V1__events.sql` already holds the join code, its unique index and `event_join_code_once_published`, which was written for this story | #192 D3 created the table with the publish in mind. Adding `V2` to change nothing would only cost every environment a migration |
| D9 | **The visibility check of #192 D5 is extracted into one `EventReader`**, used by `EventQueryService`, `TeamService` and the new `EventService` | The same six lines (event exists → active membership → `canSee`, each refusal recorded) were already copied in two services and this story would be the third. The alternative, a third copy, would also mean three places to change when US-09 and US-13 add statuses |

## 5. Edge-case matrix

Every test name starts with `US-11 AC-1`, except where another story's test is named in full.

| Case | Expected | Test |
|---|---|---|
| An EventAdmin publishes a draft | `200` with `status: Published` and the `joinLink`, version 2, the row updated with who and when, one `EventChanged`, one log line | `PublishEventIT` · `an EventAdmin publishes a draft and gets the event with its join link`; `EventServiceTest` · `publishing a draft stores it, publishes EventChanged and records who and when`; `JdbcEventsIT` · `publishing a draft writes the status, the join code and the next version` |
| Participants find it (the criterion's *then*) | The same `RegularUser` who got `404` on the draft reads the event, with its join link, right after the publish | `PublishEventIT` · `a participant who could not see the draft reads the event and its join link once it is published` |
| The join code | 27 Base64 URL-safe characters, new on every publish, unique in the table, absent from `EventChanged` and from every log line | `PublishEventIT` · `the join code is unguessable, new for each event and never logged`; `EventContractIT` · `publishing an event publishes an EventChanged that matches its JSON Schema, with no join code` |
| A join code that collides with a stored one | `event_join_code_unique` rolls the transaction back: `500`, nothing stored, published or logged (D1) | `JdbcEventsIT` · `a join code already in the table rolls the publish back instead of storing it` |
| Publishing the same event twice | `200` then `409` *This event is not a draft.*; the join code and the version stay as the first publish left them, nothing is published again | `PublishEventIT` · `publishing twice is refused and changes nothing`; `EventServiceTest` · `a second publish is refused and publishes nothing` |
| `Suspended` (from `Draft` or from `Published`) and `Closed` | `409` *This event is not a draft.*, nothing stored or published | `PublishEventIT` · `only a draft is published`; `EventServiceTest` · `only a draft is published` |
| Two publishes at once (same read) | One `200`, the other `409` *This event is not a draft.* — the loser's `UPDATE` re-evaluates against the committed row and finds it `Published`; one join code, one version, one `EventChanged` (D4) | `JdbcEventsIT` · `the second publish from the same read is refused, and the first one stands`; `EventServiceTest` · `an event another request published between the read and the write is not a draft any more, and nothing is published` |
| A draft that moved to another version meanwhile | `409` *This event changed meanwhile; read it again.*, nothing stored or published. No write of this service does that yet: it needs one that leaves the event a draft, which US-10 (#92) brings | `JdbcEventsIT` · `a publish that lands on a draft at another version is a conflict`; `EventServiceTest` · `an event changed between the read and the write is a conflict, and nothing is published` |
| A `RegularUser` member of a **draft** event | `404`, recorded as `NOT_VISIBLE` (D3), nothing stored | `PublishEventIT` · `a RegularUser cannot see a draft, so publishing it is not found`; `EventServiceTest` · same name |
| A `RegularUser` member of a **published** event | `403` *No permission in this event.* | `PublishEventIT` · `a RegularUser of a published event has no permission to publish`; `EventServiceTest` · same name |
| A non-member, a member of another event, a `FarolAdmin` who is not a member, a removed member | `404` in every case, each recorded as a refusal, nothing stored | `PublishEventIT` · `an unknown event, a non-member, another event's admin and a removed member are all the same 404`; `EventServiceTest` · `every refusal is the same not-found and is recorded` |
| An EventAdmin of event X publishing event Y | `404`; X is untouched | `PublishEventIT` · `an unknown event, a non-member, another event's admin and a removed member are all the same 404` |
| An unknown event id, well formed / a malformed id | `404` / `400` | `PublishEventIT` · `an unknown event, a non-member, another event's admin and a removed member are all the same 404`, `a malformed event id is refused with 400` |
| A body sent on the `POST` (mass assignment), another media type | The body is ignored — the operation has none, so nothing can be assigned — and the publish is still a publish | `PublishEventIT` · `a body sent with the publish changes nothing` |
| No token / expired / wrong signature / wrong issuer / wrong audience / `alg none` / HS256 / non-canonical `sub` | `401` | `SecurityIT` · `192 AC-2 every secured operation of the contract refuses a missing or invalid token with 401 Problem Details` |
| The log line of D7 | One `INFO` line with the correlation id, the pseudonymous `userId`, the event, the new status and version — no name, no e-mail, no join code | `PublishEventIT` · `the publish is recorded with who made it and when, and never with a name or the join code` |
| `EventChanged` against its JSON Schema, through the real broker to every bound queue | Valid, with the status `Published` and the new version, and no join code | `EventContractIT` · `publishing an event publishes an EventChanged that matches its JSON Schema, with no join code` |
| The contract | Every operation of the *Events* tag that Sprint B needs is served; eight operations are left for later stories (nine before this one) | `ContractIT` · `192 AC-4 the service serves exactly the operations of openapi.yaml`, `192 AC-4 eight operations of the contract belong to later stories` |

## 6. Handoff and changelog

- **24 Nov 2026 · research.** Focused pass over what this story touches, since #192, US-16 and US-17 had already covered the shared ground (tables, envelope, authorisation, the gates and the shape of the tests): the `event` row and its three publish-related constraints, `event.changed.schema.json` and its four consumer queues, the `eventChanged` payload helper that #192 left in `EventContractIT` for the first story to publish it (D5), `EventResponse.JOIN_LINK`, and **how US-12 actually joins** — `POST …/members/me` takes no code and decides from the local copy of `EventChanged` (API outline §2, `auth-users/contracts/openapi.yaml`), which is what D1's open point below is about.
- **24 Nov 2026 · implementation**, in the order of §4, with `mvn clean verify` (JDK 21) green at the end: **202 unit and 578 integration tests**, JaCoCo **940/942 lines (99.8 %)** — the two missed are still `EventsApplication.main` — and **242/242 branches (100 %)**, generated code included and no exclusion, PIT **139/139 mutations killed (100 %)**. No threshold lowered, no test disabled.
- **One gap found by the gates, in the tests, not in the code:** the first run left `Events.Write.NOT_DRAFT` uncovered in `EventService` (one line, one branch, one surviving mutation) and the `409` of D4 uncovered in the advice. Both are outcomes **no sequential request can produce** — the domain already refuses a non-draft read, so the port only reports `NOT_DRAFT` when another request published the event between this one's read and its write. Covered the way US-16 covers the same shape: the adapter's real outcomes in `JdbcEventsIT`, the answer each one turns into in `EventServiceTest` (through one `publishOutcome` knob on `InMemoryPorts`, which replaced the two booleans a first draft had) and in `ProblemDetailsAdviceTest`.
- **25 Nov 2026 · review of [#249](https://github.com/tomasoliveira21/LABDSOF/pull/249).** Two findings, both taken: the join-code **retry could not work against Postgres** (a unique violation aborts the transaction of `publish`, so the retry's `UPDATE` would fail with SQLState 25P02 and the request would end in `500` anyway), so the loop, its three attempts, `Write.CODE_TAKEN`, the `DuplicateKeyException` catch and the two retry tests are gone and D1 now says the collision rolls back; and the edge-case matrix and the changelog **named the wrong `409` for a lost publish race** — the loser's `UPDATE` re-evaluates against the committed row, finds it `Published` and gets `NOT_DRAFT`, which is what `JdbcEventsIT.secondPublishFromTheSameReadIsRefused` has always asserted. `CONFLICT` keeps its own row: it needs a write that leaves the event a draft, which only US-10 brings. After both, with `main` merged in: **200 unit and 578 integration tests**, JaCoCo **934/936 lines (99.8 %)** and **238/238 branches (100 %)**, PIT **136/136 (100 %)**.
- **Open point for US-12 (#63), raised here, not decided here:** the join code is in the link and the QR code, but **nothing checks it today** — Auth & Users joins a published event by its `eventId` alone, so the link's secrecy currently protects nothing. Two readings are defensible: the code is only a marker that the link came from the back office (then it stays as it is), or the join must present it (then `POST …/members/me` grows a body and Auth & Users needs the code, which `EventChanged` deliberately does not carry, so it would have to be read by the web app from `GET /events/{eventId}`). D1 keeps the code unguessable so either reading stays open; the choice belongs to US-12, and it is on the issue.
